# عقد API — المرحلة 3 (مسودة)

**الحالة:** مسودة مبنية على متطلبات المشروع وأسماء الجداول الـ 11 فقط. لم تُراجَع مقابل المخطط الفعلي، وأسماء الأعمدة هنا **ليست** أسماء أعمدة قاعدة البيانات. هذا عقد JSON بين التطبيق والخادم، ويتولى الخادم ربطه بالأعمدة بعد مراجعة المخطط.

## مبادئ

- المسار: `Android App → HTTPS API → PHP Backend → MySQL`. التطبيق لا يعرف قاعدة البيانات ولا أي سر.
- HTTPS فقط، JSON بترميز UTF-8، ورؤوس `Content-Type: application/json; charset=utf-8`.
- نقاط القراءة العامة تُرجع الأخبار المعتمدة فقط. أي خبر غير معتمد يُعامل كأنه غير موجود (404).
- كل مدخل يُتحقق منه على الخادم، والاستعلامات عبر PDO بـ prepared statements.
- لا تُعاد تفاصيل الأخطاء الداخلية للعميل، ولا تُسجَّل أسرار أو رموز في السجلات.
- الصلاحيات تُفرض على الخادم. واجهات الإدارة لاحقاً تحت مسار منفصل `/api/v1/admin/` بمصادقة وصلاحيات منفصلة، ولا تُخلط بنقاط المستخدم العادي.

## نقاط المرحلة 3 (قراءة فقط)

### GET /api/v1/news

معاملات: `page` (افتراضي 1)، `per_page` (افتراضي 20، أقصى 50)، `region` (معرّف المنطقة، اختياري)، `q` (نص بحث، اختياري، أقصى 100 حرف).

```json
{
  "items": [
    {
      "id": 1,
      "title": "...",
      "excerpt": "...",
      "image_url": "https://... أو null",
      "source": "...",
      "published_at": "2026-10-14T12:00:00+03:00",
      "region": { "id": "abeen", "name": "عبين" }
    }
  ],
  "page": 1,
  "per_page": 20,
  "has_more": false
}
```

### GET /api/v1/news/{id}

نفس عناصر القائمة مع الحقل `content` (نص كامل، الفقرات مفصولة بسطر فارغ). 404 إذا لم يوجد أو لم يُعتمد.

### صيغة الخطأ

```json
{ "error": { "code": "not_found", "message": "الخبر غير متاح" } }
```

رموز HTTP: 400 مدخل غير صالح، 404 غير موجود، 429 كثرة طلبات، 500 خطأ خادم (رسالة عامة).

## خارج المرحلة 3 (المرحلة 4 وما بعدها)

تسجيل الدخول بـ Google (يتحقق الخادم من الرمز ويُصدر رمز جلسة)، التصويت (صوت واحد لكل مستخدم لكل خبر بقيد فريد في قاعدة البيانات)، التعليقات، التوثيق ورفع الهوية، الإشعارات، الإعلانات، لوحة الإدارة.

## قرارات تنتظر المخطط الفعلي

1. أسماء الأعمدة، وقيمة الحالة التي تعني «معتمد»، وحقل التاريخ المعتمد للعرض.
2. تمثيل المنطقة (عمود في `news` أم جدول مستقل)، فالمسودة تفترض معرّفاً واسماً.
3. تخزين الصور: رابط مباشر أم ملفات على الاستضافة.
4. آلية البحث: `LIKE` أم فهرس FULLTEXT إن كان موجوداً، ومدى ملاءمته للعربية.
5. ثغرة ربط جدول `keywords` بالأخبار ما زالت مفتوحة؛ لا تؤثر على قراءة المرحلة 3 لكنها تلزم قبل مرحلة الإدارة.

## مخاطر الاستضافة يجب قياسها قبل البناء عليها

- استضافة InfinityFree المجانية معروفة بحجب بعض الطلبات غير المتصفحية بصفحة تحدٍّ JavaScript، وهذا قد يكسر استدعاء الـ API من التطبيق. **هذا خطر محتمل لم أتأكد منه**؛ يُحسم بتجربة `ping.php` المرفق من خارج المتصفح (انظر أدناه).
- قيود الاتصال الصادر من PHP (مطلوب للتحقق من رمز Google وجلب الأخبار من المصادر) وحدود الطلبات اليومية يجب التحقق منها فعلياً.
- إن ثبت أن الاستضافة لا تكفي، تُناقَش بدائل قبل أي قرار، ولا يُستخدم أي بديل مدفوع دون موافقتك.

# المرحلة 4 — الحسابات والتفاعل (مسودة)

**الحالة:** مسودة لم تُنفَّذ في الخادم بعد. التطبيق يستخدم حالياً تنفيذاً تجريبياً محلياً (`DemoAuthRepository` و`DemoInteractionRepository`) خلف واجهات ستُستبدل بتنفيذ يتصل بهذه النقاط.

## نقاط الحسابات

### POST /api/v1/auth/google

الجسم: `{ "id_token": "..." }` (رمز Google الذي يحصل عليه التطبيق عبر Credential Manager).

الخادم يجب أن: يتحقق من توقيع الرمز، و`aud` يطابق معرّف عميل الخادم، و`iss` من Google، و`exp` غير منتهٍ، و`email_verified=true`؛ ثم ينشئ المستخدم أو يحدّثه ويُصدر رمز جلسة عشوائياً.

```json
{
  "access_token": "opaque-random-token",
  "expires_at": "2026-11-14T12:00:00+03:00",
  "user": { "id": 1, "display_name": "...", "verification": "none" }
}
```

- رمز الجلسة عشوائي (32 بايتاً على الأقل) ويُخزَّن في القاعدة **مجزّأً (hash)** لا نصاً صريحاً.
- الطلبات المحمية تحمل `Authorization: Bearer <token>`، والخادم يتحقق من الرمز وانتهائه في كل طلب.
- قيم `verification`: `none` و`pending` و`approved` و`rejected`.

### GET /api/v1/me

يرجع المستخدم الحالي. 401 إذا الرمز غير صالح أو منتهٍ.

## نقاط التفاعل

### POST /api/v1/news/{id}/vote

الجسم: `{ "vote": "credible" | "not_credible" }`. يرجع الملخص `{ "credible": n, "not_credible": n, "my_vote": "credible" | "not_credible" | null }`.

- **صوت واحد لكل مستخدم لكل خبر يُفرض بقيد فريد (UNIQUE) على (الخبر، المستخدم) في قاعدة البيانات**، والكتابة بـ upsert داخل معاملة. لا يُكتفى بالتحقق في PHP.
- تغيير الصوت يستبدل القديم. الخبر غير المعتمد يرجع 404.

### GET /api/v1/news/{id}/votes

الملخص نفسه. بدون رمز يرجع `my_vote: null`.

### GET /api/v1/news/{id}/comments و POST /api/v1/news/{id}/comments

الجسم: `{ "text": "..." }`، من 1 إلى 500 حرف بعد القص. يتحقق الخادم من الطول بعدد الأحرف (UTF-8 وليس البايتات)، ويحدّ معدل النشر لكل مستخدم (429). نص التعليق يُعرض نصاً عادياً دائماً.

## قرارات مفتوحة تحتاج قرارك

1. **من يحق له التصويت والتعليق؟** الافتراض في التطبيق الآن: أي مستخدم مسجّل. البدائل: الموثّقون فقط، أو التعليق للجميع المسجلين والتصويت للموثّقين. القاعدة في مكان واحد (`InteractionRules`) وتتغير بسهولة، لكن الخادم هو من يفرضها فعلياً.
2. **هل تُراجَع التعليقات قبل ظهورها؟** (مراجعة مسبقة أم نشر مباشر مع إخفاء لاحق). يؤثر على جدول `comments` وعلى لوحة الإدارة.
3. **التحقق من رمز Google يحتاج اتصالاً صادراً من PHP** لجلب مفاتيح Google العامة. استضافات مجانية كثيرة تقيّد الاتصال الصادر، وهذا غير مفحوص على InfinityFree ويجب قياسه قبل الاعتماد عليه. إن حُجب فالبدائل تُناقَش معك.
4. **معرّف عميل Google (Client ID)** تنشئه أنت من Google Cloud (مجاني): معرّف عميل Web للخادم، وعميل Android يرتبط ببصمة SHA-1 لمفتاح التوقيع. لا يُرسَل أي سر (Client Secret) إلى التطبيق.
5. **تخزين رمز الجلسة على الهاتف** يتطلب تخزيناً مشفراً بمفتاح Android Keystore. يُنفَّذ مع تسجيل الدخول الحقيقي، ولا يوجد تخزين رموز في الكود الحالي.
6. **قيد التصويت الفريد:** لم أفحص مخطط `news_votes` الفعلي. يجب التأكد أن القيد الفريد موجود فيه، وإلا فإضافته تعديل على مخطط معتمد يُشرح سببه قبل تنفيذه.
